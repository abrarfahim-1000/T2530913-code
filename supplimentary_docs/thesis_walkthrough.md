# Thesis Walkthrough

## 1. Grid terms

| Term | Meaning |
|---|---|
| Bus | A substation — a junction where lines, generators and demand connect. A node in a graph. |
| Line | A transmission line joining two buses. An edge. |
| Load | Electricity demand at a bus. |
| Generator | A power plant feeding the grid at a bus. |
| Power flow | The calculation for how much power ends up on each line. Electricity takes every available path at once in proportion to impedance, so it cannot be divided up directly. Solving it is iterative and therefore slow. |
| Thermal limit | How much current a line carries before it overheats and gets disconnected. |
| rho (ρ) | Loading ratio: actual flow divided by thermal limit. 0.4 means the line is at 40% of capacity, 1.0 means it is at the limit, above 1.0 is an overload. `loading_pct` is the same number as a percentage. |
| Per unit (pu) | Voltage as a fraction of the line's design voltage. 1.0 pu is nominal. It exists so a 138 kV line and a 345 kV line can be compared on one scale. |
| Trip | A protective relay automatically disconnects a line, usually from overload. It is automatic, not a decision. |
| Cascade | A line trips, its power redistributes onto neighbours, they overload and trip, and so on. This is how blackouts happen. |
| Grid code | The rulebook a national operator publishes for equipment connected to its grid. These are the PDFs we extracted from. |

**N-1 security** is the rule that the grid must survive the loss of any single component. Operators
check it continuously: for every line, if that line failed right now, would anything else go over
its limit? Each hypothetical failure is a **contingency**.

Checking one contingency requires a full power-flow solve. A grid with 186 lines needs 186 solves,
repeated every few minutes as demand changes. A model that predicts the answer from the current
state skips the solve. That is the task.

## 2. The data

We used Grid2Op with the lightsim2grid backend, on three grids.

| Grid | Size | Role |
|---|---|---|
| `l2rpn_neurips_2020` | 36 buses, 59 lines | Training. The only grid the model learns from. |
| `l2rpn_case14_sandbox` | 14 buses, 20 lines | Test only, smaller, never seen. |
| `l2rpn_wcci_2022` | 118 buses, 186 lines | Test only, larger, never seen. |

We never train on the two test grids.

A **chronic** is Grid2Op's term for one scenario — a time series of how demand and generation
evolve. The training grid has 576. We step the simulator forward and record the full state at each
step. Faults are injected at 5% per step on a random line, with a 20% reconnection probability, so
the data contains disturbances and cascades rather than only calm operation.

### Labels

For each frame and each line we ask the simulator, via `obs.simulate()`, whether tripping that
specific line would push any remaining line over its thermal limit. This runs the real power-flow
solve for the hypothetical.

One frame therefore produces a vector of labels, one per line:

```
frame 1: [safe, safe, VIOLATION, safe, VIOLATION, safe, ...]   59 entries
frame 2: [safe, VIOLATION, safe, safe, safe, safe, ...]
```

Totals: 702,618 labels from the training grid, 118,502 from case14, 742,472 from WCCI. About 20%
of contingencies are violations.

Some cells cannot be labelled, because the line is already disconnected or the solver diverges
(under 1% of cells). These are marked `-1` and excluded from the loss. They are missing labels, not
safe ones. Treating them as safe would train the model that disconnecting an already-dead line is
harmless, which is true but uninformative, and it would distort the metrics.

## 3. The first task, and why it was dropped

The original task was a 4-class classifier: read the grid state, output `normal`, `overload`,
`line_trip` or `cascade`. We trained a Graph Attention Network on it over three rounds of
architecture work and reached macro F1 0.8277.

The labels were generated by this function:

```python
if max_rho >= 1.0:              return "overload"
if active_lines == n_line:      return "normal"
if active_lines == n_line - 1:  return "line_trip"
return "cascade"
```

That is four if-statements over two numbers, both of which are already in the model's input. We
checked how closely those four rules reproduce the stored labels: **zero disagreements across all
315,000 records** of both datasets.

This makes the task useless for our purpose. The thesis asks whether a symbolic rule layer adds
value on top of a neural network. On this task the rule layer scores 100% and the network scores
83%, because the rule layer *is* the labelling function. The measurement was determined before it
ran.

The correct reading is that the benchmark was mis-specified, not that rules beat neural networks.
The labelling function was defined over the same observation the model was given, so the label
carried no information the input did not already contain. The same labelling scheme appears in
published work on Grid2Op-derived datasets.

We dropped the task.

## 4. The two forecast tasks, and why they were dropped

The next idea was forecasting: predict whether a fault occurs in the next H timesteps. The future
is not in the input, so no rule can restate it.

**Any-fault forecast.** Faults are injected by `np.random.rand() < 0.05` on a uniformly random
line, so fault onset is unpredictable by construction, and those random trips are 71–88% of all
positive labels. Measured before training: the best possible threshold scores 1.00× the
all-positive baseline at every H ≥ 3. Nothing beats a model that always answers "at risk".

**Overload-only forecast.** Overloads come from demand rising, so this is predictable, and a single
threshold beat the trivial baseline by 2.76×. But gradient boosting on 30 features reached F1 0.163
against the single threshold's 0.160, with worse average precision. Trend features over lags 1, 3
and 6 changed nothing. A snapshot carries no information about future demand.

These two results establish that a task needs two checks, not one:

1. Non-vacuity — the target is not predictable from the base rate alone.
2. Non-exhaustion — a model beats the best single rule, not just the base rate.

The overload target passed the first and failed the second. Work that reports only the first will
accept tasks on which the neural component does nothing.

## 5. N-1 screening

For every line: if this line trips now, does anything violate a limit? Probe on 300 frames, 17,652
contingency labels:

| Predictor | F1 |
|---|---:|
| Always say violation | 0.311 |
| Best threshold on the grid's overall max loading | 0.289 |
| Best single rule: loading on the line being removed | 0.608 |
| Model with network context | 0.868 |

Producing the label requires a power-flow solve on a grid state that does not exist yet, so no rule
over the current observation can restate it. Row 2 shows this empirically: the obvious global
summary statistic scores worse than the trivial baseline.

There is also room for a model to do work. A local rule reaches 0.608 and a network-aware model
reaches 0.868.

96–99% of frames are strictly mixed — within one grid state, some contingencies violate and others
do not. A single per-frame answer is therefore wrong for most lines in almost every frame. The
quantity being predicted lives on the edges, not on the graph.

## 6. The GNN

Three `GATv2Conv` layers with batch norm and ELU. Buses are nodes with 8 features, energized lines
are edges with 8 features. Disconnected lines are pruned from `edge_index`; if they are left in, a
grid with a tripped line is structurally identical to a healthy one.

GATv2 rather than GAT, because GAT computes attention before concatenating query and key, which
makes the attention ranking static across nodes and rank-collapses on a 36-node graph.

Nothing is pooled. For each line *k* the head reads that line's own edge:

```
[ h_or ‖ h_ex ‖ edge_attr_k ‖ x_or ‖ x_ex ] → MLP → one logit for line k
```

Both endpoint embeddings, the edge features, and the raw unprocessed endpoint features. Two
reasons:

- Pooling would erase the answer. 96–99% of frames are mixed, so compressing the graph into one
  vector removes the per-line distinction the task is about.
- The head has no dependence on line count, so the same checkpoint runs on 20-line case14 and
  186-line WCCI unchanged. The previous classifier had a per-bus head emitting `n_nodes` logits and
  had to be disabled for cross-topology evaluation.

The raw features are concatenated in because attention and normalisation can transform
`sum_headroom` (spare capacity at the bus) and `sum_abs_p` (flow through it) into something
unrecognisable, and those two quantities are the physics of post-trip redistribution — the lost
power must be absorbed by spare capacity nearby. Passing them through unmodified lets the head form
the flow-to-spare-capacity ratio directly.

Splits are chronic-level 70/15/15. Frames within a chronic are consecutive timesteps, so a
frame-level split would put timestep 40 in train and 41 in test and leak cascade sequences.

### Results

Held-out test split, 113,205 contingencies:

| | F1 | |
|---|---:|---|
| Always-say-violation baseline | 0.3104 | is the task non-vacuous |
| Best rule on the removed line's loading | 0.4639 | the bar to clear |
| Message passing disabled, endpoints only | 0.8411 | ablation |
| Full GNN | 0.8872 | 1.91× the rule, AP 0.9549 |

Message passing contributes +0.058, which is the evidence that graph structure carries information
beyond the two endpoint buses.

Every model F1 in this document was measured at eval batch size 64, and that qualifier is
necessary. The model uses `BatchNorm(track_running_stats=False)`, meaning it computes normalisation
statistics from the current batch at inference rather than from stored running averages. Batch
composition therefore changes the logits. The same checkpoint on the same split scores 0.8972 at
batch 64 and 0.9255 at batch 512. The positive count and the rule baseline are identical across
those runs, so the variation is in the forward pass and not in the data.

The shield comparison is unaffected, because both arms run through the same forward pass. Across
the same batch-size change its delta moves from +0.0082 to +0.0072 and its intervention precision
from 0.938 to 0.930. Absolute model scores are not stable; the deltas are.

Cross-topology:

The model outputs a score per line, and a cutoff turns that score into a yes/no answer. Where the
cutoff goes changes the F1, so the cutoff has to be chosen somehow. We choose it once, on the
training grid's validation split, and then use that same value on every grid. The alternative —
trying every cutoff on each grid and reporting whichever scored best — uses the answer key to make
the choice and is not available in deployment.

| Grid | All-positive | Best rule | Model |
|---|---:|---:|---:|
| neurips2020 (trained on) | 0.3104 | 0.4639 | 0.8956, 1.93× the rule |
| case14 (unseen, smaller) | 0.4345 | 0.5392 | 0.4167, 0.77× — loses to the rule |
| wcci2022 (unseen, larger) | 0.3969 | 0.4915 | 0.5577, 1.13× the rule |

On case14 the model loses to a single threshold, and also to the all-positive baseline: 0.4167
against 0.4345, or 0.96×. On that grid it is worse than answering "violation" for every
contingency.

Scaling up to a 3× larger grid costs less than scaling down. The likely cause is that case14 runs
lines at 14 and 20 kV, voltages the model never saw during training, but this has not been tested.

Choosing the cutoff per grid instead would give 0.8972, 0.4477 and 0.5721. Those are higher because
the answer key was used to pick them, and the effect is larger on the unseen grids: +0.0015 at home
against +0.0310 on case14. A foreign grid shifts the model's scores, so a cutoff fixed on the
training grid sits further from that grid's best value. Those figures appear in the docs only as a
ceiling, never as a result.

## 7. Stage 1: extraction

16 standards documents: NERC Reliability Standards, the GB Grid Code, the Bangladesh Grid Code,
ENTSO-E network codes, IEEE 1547 and others.

`pdfplumber` extracts the text. We chunk at 1,200 characters with 200 overlap, roughly 300–400
tokens of dense prose, and send each chunk to Qwen3 through Ollama. The prompt asks for a JSON
array where each rule has an id, a source citation, an entity type, a condition as a Python boolean
expression, an action, a severity and a one-sentence explanation.

Three properties of this prompt:

**The vocabulary is open.** The prompt says to use variable names that describe the engineering
quantities in the standard, with no pre-defined list. We tried closing it against the simulator
vocabulary twice and extraction returned zero rules both times. Many of these standards are mostly
about frequency and timing, which the simulator does not model, so a restricted model correctly
answers `[]` for nearly every chunk and stage 2 starves. Keeping stage 1 open also makes the
untranslatable file a usable audit trail rather than an empty one. A test now fails if the prompt
is closed again.

**Violation polarity.** The condition must be `True` when the rule is violated, so a stated normal
range gets inverted: `"voltage shall remain within 0.95–1.05"` becomes
`voltage_pu_min < 0.95 or voltage_pu_max > 1.05`. This instruction later turned out to cause a
class of bug — see stage 2.

**Exhaustiveness.** Return `[]` only for text that states no constraint: title pages, contents,
administrative clauses about record-keeping.

Result: 2,463 candidate rules. The stage is complete and is not re-run.

Two implementation details. Thinking has to be suppressed at the API level with `think=False`, not
with a `/no_think` prefix, because newer Qwen builds ignore the prefix and the reasoning trace
breaks JSON parsing. Rule IDs are made globally sequential across all chunks and documents before
anything else runs.

## 8. Stage 2: translation

Stage 1 produces rules in the standards' own terms, referencing quantities like
`relay_loadability_limit_pct` and `initial_delay_seconds` that the simulator does not report. Stage
2 rewrites each condition into a fixed vocabulary of 14 observable quantities, or marks it
untranslatable.

| Group | Variables |
|---|---|
| voltage, loading, topology | `voltage_pu_min`, `voltage_pu_max`, `loading_pct`, `rho_max`, `n_tripped_lines`, `any_line_tripped` |
| power flow | `active_power_mw_max`, `reactive_power_mvar_max`, `apparent_power_mva_max`, `power_factor_at_max_load`, `current_a_max` |
| system balance | `total_generation_mw`, `total_load_mw`, `generation_load_imbalance_pct` |

The vocabulary was 6 variables until we noticed we were ignoring power flows and generation totals
that every record already carried. Widening it to 14 took the share of candidates that are
expressible from 7.9% to 28.1%.

### The five translation cases

**Case 1, synonym.** The standard names an observable quantity differently.

```
"current_amps > 1200"        →  "current_a_max > 1200"
"line_loading_percent > 95"  →  "loading_pct > 95"
```

**Case 2, unit conversion.**

```
"voltage_kv < 130" on a 138 kV line  →  "voltage_pu_min < 0.94"
"flow > 0.5 GW"                      →  "active_power_mw_max > 500"
```

Only when the conversion is unambiguous. If a rule states a kV threshold without stating the
nominal, it cannot be converted — 130 kV is normal on a 345 kV line and severe on a 138 kV line.
Those are marked untranslatable.

**Case 3, aggregation binding.** Standards refer to "the voltage" or "the loading" as a scalar, but
the grid has many lines. The direction of the limit determines which aggregate is meant. An
under-limit binds to the minimum, since if the lowest value is acceptable then all are. An
over-limit binds to the maximum.

```
"voltage shall not fall below 0.9"  →  "voltage_pu_min < 0.9"
"voltage shall not exceed 1.1"      →  "voltage_pu_max > 1.1"
```

Binding an under-limit to the maximum produces a rule that almost never fires.

**Case 4, proxy substitution.** Standards express limits relative to an equipment rating. A rating
belongs to one specific circuit, and `loading_pct` is already flow divided by rating, so the ratio
replaces the absolute figure.

```
"shall not exceed 100% of the continuous rating"  →  "loading_pct > 100"
"loaded beyond its emergency rating"              →  "rho_max > 1.0"
```

The ratio is never OR-ed with the absolute figure. An offshore rating schedule reading
`Post-Fault Continuous | 100% | Line | 580 Amps | 132 MVA` states one limit in three units, but was
read as three limits and produced:

```python
loading_pct > 100 or current_a_max > 580 or apparent_power_mva_max > 132
```

`current_a_max` is the largest current on any line in the grid, while 580 A is one named circuit's
nameplate. The rule therefore asks whether the busiest line anywhere exceeds some other line's
rating, which is true on a healthy grid. It fired on 100% of healthy frames on all three grids. The
prompt now carries this case as a worked example and names the defective string explicitly.

**Case 5, scope versus predicate.** Clauses often combine which equipment is governed with what is
required of it. In "Modules above 50 MW shall keep voltage within 0.95–1.05", the 50 MW figure
selects which modules are covered and is not part of the violation test. Translating the whole
sentence gives:

```python
active_power_mw_max > 50 and voltage_pu_min < 0.95   # wrong
```

which makes the rule fire on equipment size rather than grid condition.

### Two categories that are discarded

**Compound conditions are discarded, not trimmed.** `voltage_pu_min < 0.9 and time_seconds > 3`
cannot become `voltage_pu_min < 0.9`, because the standard tolerates a brief dip. The trimmed rule
would flag states the standard permits while citing that standard as its source. The whole rule is
dropped and the reason names the missing variable.

**Ride-through ranges are discarded.** A ride-through or no-trip-zone requirement says equipment
must stay connected through a brief abnormal excursion — "shall remain connected for voltages
between 0.7 and 0.9 pu for 3 seconds". As a constraint, `0.7 < v < 0.9` fires at nominal voltage,
since 1.0 is outside the band. As a statement of normal operation it is false at nominal. The
actual requirement concerns not tripping during a disturbance, which needs protection status and
duration, neither of which is observable.

### Rule roles

The stage-1 instruction to invert every stated normal range into a violation was itself generating
broken rules, so rules now carry a role.

| Role | Meaning | Effect |
|---|---|---|
| CONSTRAINT | Condition `True` means the standard is violated | The shield blocks |
| AFFIRMATION | Condition `True` means telemetry is consistent with a named state | Supporting evidence only, never blocks alone |

Grid codes are written mostly as "shall remain within" and "shall be capable of", which is
affirmation-shaped. Forcing everything into constraint polarity produced predicates that fire at
nominal voltage.

### The first run was a parsing bug

Stage 2 initially reported 6 translatable rules out of 2,463, which reads as a result about how
poorly standards match simulators. It was not. 2,190 of 2,463 rules (88.9%) came back
`NO_VERDICT`, meaning they were never assessed; only 233 received a verdict at all.

Every worked example in the prompt omitted the `rule_id` field while the Pydantic schema required
it, so every response failed validation and was dropped by a bare `except ValidationError: pass`.
The model was answering correctly and the answers were discarded.

A pipeline that cannot distinguish "assessed and rejected" from "never assessed" reports the second
as the first, and the summary statistics are identical either way. There is now a tripwire that
logs an error above 20% `NO_VERDICT`, and a test that fails if the prompt examples lose their
`rule_id`.

After the fix, 58 rules translated, with every rule receiving a verdict.

## 9. Stage 2.5: the polarity guard

Deterministic, no model and no GPU. It asks whether a rule fires on a healthy grid.

We take recorded frames labelled `normal`, substitute the measured values into each condition, and
count how often it evaluates `True`. A constraint that fires on healthy grids is wrong by
definition.

The fire-rate distribution is bimodal: 33 rules fired on ≤ 1% of healthy frames, 25 on ≥ 75%, and
nothing between 10% and 90%. The 0.5 cutoff is therefore measured rather than chosen. This
reproduced on a separate extraction run.

Result: 32 rules kept out of 58.

### Base kV

Per unit means voltage divided by the line's base kV. We initially used a flat divisor of 150 kV.

case14 runs lines at 14, 20 and 138 kV. A 20 kV line divided by 150 reads as 0.13 pu, which every
undervoltage rule reads as a collapse. The training grid has 7 lines at 345 kV, reading as 2.4 pu.
The false block rate was near 100%. Separately, disconnected lines report `v_or = 0`, so an
unmasked minimum fires every undervoltage rule on any frame with a disconnection.

We now use per-line base kV with energized-line masking. That raised a second question: where base
kV comes from. Two methods disagree.

| Grid | Backend nominal | Measured median | Gap |
|---|---|---|---|
| neurips2020 | 138, 345 kV | 145.9–149.0, 361.2–369.6 | 6.63%, on 59 of 59 lines |
| case14 | 14, 20, 138 kV | 14.9, 21.2–22.0, 139.5–142.1 | 4.23%, on 16 of 20 lines |

The gap is near-uniform (147/138 = 1.066, 365/345 = 1.058), which is the signature of generator
voltage setpoints held at 1.05–1.06 pu, the IEEE test-case convention these grids inherit. It is
not a defect in the grids.

We use the backend nominal. The alternative, measuring the median voltage in our own data and
calling it 1.0, sets the healthy centre using the same data the rules are then tested against.
Given that section 3 is about discovering a benchmark that was determined before it ran, a second
self-calibration inside the shield's own context is not defensible.

The consequence is that healthy frames read about 1.06 pu rather than 1.00 pu, so a standard
±5% band like `voltage_pu_max > 1.05` fires on nearly every healthy frame and is rejected by the
guard. Stated as a finding: grid-code voltage bands are calibrated to utility operating practice
rather than to IEEE test-case setpoint conventions, and do not transfer to these reference grids
without rebasing.

### The audit

The guard asks whether a rule is wrong. A separate deterministic pass asks whether it can do
anything. A constraint that fires on 0% of healthy frames passes the guard, but if it also fires on
0% of abnormal frames it can never block.

| Verdict | Count | Example |
|---|---:|---|
| INERT | 4 | `voltage_pu_max > 1.5`, never fires on any class on any grid |
| UNINFORMATIVE | 7 | wide voltage bands holding on `normal` and `overload` alike |
| TOPOLOGY_DEPENDENT | 11 | fires on abnormal frames on some grids only |
| USEFUL | 10 | all ten are `loading_pct > 100` |

Voltage cannot discriminate here because Grid2Op's faults are thermal. Lines overheat and trip
while voltage stays in band through overload and cascade alike. The best margin any voltage rule
achieved was +0.006.

Two caveats. `loading_pct > 100` scores 1.000 on abnormal frames partly because the `overload`
label is itself `rho_max >= 1.0`, so the USEFUL verdict is contaminated by label restatement and is
not independent validation. And the audit scores against classify labels while the live task is
N-1, so it is triage rather than a shield evaluation.

## 10. Stage 3: validation

Each surviving rule is sent, with the source text it came from, to a different model — Nemotron-3
Nano 30B — acting as an auditor. Using a different model keeps validation independent of
extraction.

The auditor checks seven things:

1. Does the source text state this requirement?
2. Is the threshold value correctly parsed?
3. Is the entity type correct? An imprecise entity alone is not grounds for rejection; return a
   correction instead.
4. Does the condition use only the 14 variables, with legal Python syntax?
5. Is the role correct — a genuine violation test, or a statement of normal operation that was
   wrongly inverted?
6. Is this a ride-through range? If so, reject.
7. Healthy-grid self-check: substitute `voltage_pu_min = 1.0`, `loading_pct = 40`, `rho_max = 0.4`,
   `n_tripped_lines = 0` and so on. A constraint that evaluates `True` on those values is wrong. An
   affirmation of `normal` that evaluates `False` is wrong.

Each rule returns `CONFIRM`, `CORRECT` with fixed fields, or `REJECT`, plus a one-sentence reason.

### The first run

31 of 32 rules were rejected. `validate.py` incremented a counter and discarded the verdict object,
including the `reason` field that the schema carried and the model had populated, so there were 31
rejections and no explanations. That cannot be distinguished from a broken prompt.

Two things were checked before re-running, both without a model:

- Criteria 4 and 7 are mechanically checkable. A substitution pass found 32 of 32 rules passing
  both, and only 2 tripping criterion 6. At most 2–4 of the 31 rejections could rest on the
  prompt's explicit criteria.
- At least one rejection is wrong. TPL-001-5.1 Table 1(f) states "Applicable Facility Ratings shall
  not be exceeded". R_167 renders that as `loading_pct > 100`, CONSTRAINT, and was rejected.

Criterion 1 asked whether the constraint is *stated* in the source text. That was written for
stage-1 candidates, whose conditions were still in the standard's own terms. Applied to a stage-2
condition it cannot be satisfied, because translation's purpose is to move the condition out of the
standard's language. "Applicable Facility Ratings shall not be exceeded" becoming
`loading_pct > 100` is a correct translation and is never stated in the text.

### The A/B

Same 32 rules, same model, temperature 0.0, differing only in criteria 1–3. Criteria 4–7 and the
output contract are a shared string in the code.

| Arm | Question | Confirmed | Rejected |
|---|---|---:|---:|
| `strict` | Is the constraint stated in the text? | 1 | 31 |
| `translated` | Is it a faithful operationalization? | 11 | 21 |

`strict` reproduced the first run exactly, with the same count and the same survivor. The outcome
is nested: everything `strict` confirmed, `translated` also confirmed, and nothing was confirmed by
`strict` alone. The entire difference is the ten `loading_pct > 100` rules, which moved as a block.

### The rejection reasons were fabricated

| Rule | Reason given |
|---|---|
| R_167 | "uses an undefined variable `loading_pct` and the threshold 100 is not explicitly stated" |
| R_1443 | "uses '100' which is not a valid variable" |
| R_858 | "includes a unit (100.0), violating the allowed syntax" |
| R_260 | "includes non-Python syntax such as 'or' without proper parentheses" |
| R_1717 | "the correct variable is `loading_pct`, but ... incorrectly uses `loading_pct > 100`" |

`loading_pct` is in the vocabulary block injected into that same prompt. Numeric literals and `or`
are permitted by criterion 4. `100.0` is a float, not a unit. R_1717 contradicts itself within one
sentence.

Forced by criterion 1 into a rejection it could not justify on the merits, the auditor cited the
vocabulary criterion and invented a violation of it. Eleven of the 31 rejections cite a criterion-4
breach that the deterministic pass shows does not exist. The verdicts were stable across runs while
the stated reasoning was invented, and this is only visible if the reasons are persisted.

`validate.py` now writes every rejection with its reason and logs an error above an 80% rejection
rate.

### The 21 shared rejections

Most are correct, and several required reading the document in a way the deterministic guard
cannot:

- Three PRC-024 rules: the attachments give minimum time durations for voltage excursions, not a
  continuous limit. Correctly identified as ride-through curves.
- Four ENTSO-E rules: Table 6.1 gives a minimum operating time of 60 minutes for the 0.85–0.90 pu
  range, so an affirmation of `normal` is inconsistent with a time-bound requirement. Sharper than
  the fire-rate analysis, which only saw them firing at 1.00.
- Two rules where the source states ±5% for 400 kV and +10%/−15% for 230 kV, not a flat 0.90/1.10.

About 3 rejections are wrong and 4 more should have been `CORRECT` rather than `REJECT`. The
validated corpus is better than the input, not clean.

### The final corpus

| rule_id | Role | Condition |
|---|---|---|
| R_858 | CONSTRAINT | `loading_pct > 100.0` |
| R_916 | CONSTRAINT | `loading_pct > 100` |
| R_1443 | CONSTRAINT | `loading_pct > 100` |
| R_1154 | AFFIRMATION | `voltage_pu_min >= 0.9 and voltage_pu_max <= 1.1` |

End to end: 2,463 candidates → 58 translated → 32 guarded → 4 validated. A yield of 0.16%.
Affirmation coverage is `normal` only, across three runs, so the shield's Option B counterfactual
is unmeasurable on this corpus.

## 11. The knowledge graph

The graph records where each rule came from:

```
Document → Clause → Rule → ServedRule → Predicate → Variable
```

36 nodes, 40 edges. It contains no buses, line indices or grid names, so one graph serves all three
grids.

The deduplicated rule file shows 3 thermal rules. The graph shows those 3 are stated in 10 clauses
across 4 documents by two identified standards bodies. The flat file hides this by concatenating
sources into one string.

The `Predicate` layer exists because deduplication keys on `(entity, condition)`, which splits one
physical check into three records purely from extractor noise: the same check was labelled `Line`
in one standard and `Facility` in another, and written `100` in one clause and `100.0` in another.
The graph parses conditions with `ast` and canonicalises numeric literals so they collapse. This is
a view, not a substitution — it never changes what is served, because collapsing three served rules
into one would move `highest_severity`.

### v1 was deleted

The first version organised the graph around grid topology: a node per bus, a node per line, rules
attached by entity. It failed twice over.

- Only 3.5% of extracted rules name a specific bus or line, so 6,375 of its 6,632 edges (96%) were
  noise onto a single catch-all node.
- It was built from one grid's metadata, so it could not serve the other two topologies, even
  though the rules are grid-independent.

Nothing imported it. Its output file had vanished from disk months earlier without anything
noticing.

### Never route by entity

`R_1443` is labelled `Facility` and `R_916` states the identical check labelled `Line`. Retrieving
rules by walking entity edges drops one of them from any line-level query. Both providers serve
every rule for every prediction, and discrimination comes from the conditions. A test bans grid
indices from the graph.

Retrieval through the graph returns the same rules as the flat file, verified field by field on all
three grids and pinned by a test. It changes no measured number.

## 12. The shield

Every model prediction passes through it. There is no bypass.

```
model says "secure"    + base case violates a CONSTRAINT rule  →  BLOCK
model says "secure"    + base case clean                       →  PASS
model says "violation" + anything                              →  PASS
```

N-1 security presupposes a secure base case. If the grid is already over a limit, it cannot be
declared safe against the loss of a further component, regardless of what the contingency analysis
would show.

The asymmetry is deliberate. Predicting a violation on a calm grid is a false alarm, which is
wasteful but fails toward caution. Predicting "secure" on a grid already over its limits is the
error that causes a blackout. Only that direction blocks.

Affirmation rules never block on their own; absence of support is recorded so a stricter gate can
be reported without paying its false-block rate.

### Results

The threshold was selected once on the training grid's validation split and held fixed across all
three grids.

| Grid | Model | + shield | Change | Missed violations | Precision when it acts |
|---|---:|---:|---:|---|---:|
| neurips2020 (trained on) | 0.8956 | 0.9038 | +0.0082 | 2,041 → 1,710 | 93.8% |
| case14 (unseen) | 0.4167 | 0.4188 | +0.0021 | 18,592 → 18,497 | 92.2% |
| wcci2022 (unseen) | 0.5577 | 0.6253 | +0.0676 | 68,166 → 47,101 (−31%) | 93.4% |

On wcci2022 the shielded score of 0.6253 exceeds the 0.5721 the raw model reaches on that grid when
allowed to tune its threshold against the answers. Nothing inside the model changed.

The precision column is flat. The gate is right about 93% of the time on the training grid and
about 93% on grids it has never seen, while the model goes 0.90 → 0.42 → 0.56. The gate enforces a
physical principle rather than a learned pattern, so its accuracy does not depend on topology.

What changes off-distribution is how often the gate can act — 0.31%, 0.087% and 3.04% of
contingencies — and how much of the model's error sits where the rule can reach it: 16.2%, 0.51%
and 30.9%.

### A superseded reading

An earlier version of this analysis reported that the gate was a coin flip on the training grid
(51.4%) and reliable only off-distribution (86–92%). That is void.

The 51.4% averaged two rule families. The voltage rules, which came from misread ride-through
tables, were right 13–20% of the time. The thermal rules were right 92–94%. On the training grid
the voltage rules dominated, at 478 of 831 interventions, and pulled the average down.

Stage 3 removed those voltage rules on textual grounds, having never seen fire-rate data. With them
gone the precision is flat. Dropping 28 of 32 rules improved or held every metric on every grid.

A rulebook that is mostly bad rules does not perform at a discount to the good version. It performs
at the average, and the average hides the good rules.

### Choosing the cutoff: which error to prefer

The cutoff has to be picked by optimising something, and we pick it by maximising F1. F1 treats the
two errors as equally costly: one missed violation counts the same as one false alarm. The gate
described above is built on the opposite assumption, since a missed violation can cascade and a
false alarm only wastes someone's time.

Rather than invent an exchange rate between the two, we measured the whole trade. The threshold is
still chosen on the training grid's validation split and held fixed everywhere; only the objective
changes. F-beta with beta above 1 prices a missed violation at beta squared false alarms.

| Grid | F1 (used) missed | F2 missed | extra false alarms per missed violation avoided |
|---|---:|---:|---:|
| neurips2020 | 2,041 | 987 | 3.2 |
| case14 | 18,592 | 16,390 | 2.5 |
| wcci2022 | 68,166 | 57,132 | 4.2 |

So halving the training grid's dangerous errors is possible, and costs about three false alarms for
each one avoided, plus 0.04 F1.

We kept F1. It is the standard metric, it keeps the numbers comparable with other work, and both
arms of the shield comparison are scored the same way so the delta stays fair. Picking any other
point on that curve would require knowing what an alarm actually costs an operator relative to a
cascade, and nobody has measured that for these grids. The trade is reported rather than resolved.

We did check that the shield's behaviour does not depend on this choice. Re-scored at the F2
threshold, the gate's precision when it intervenes is 0.937, 0.933 and 0.932, against 0.938, 0.922
and 0.934 at F1. Its benefit shrinks, because a lower cutoff produces fewer "secure" predictions
and therefore gives the gate less to veto, but its accuracy does not move.

### Convergence

Two independent filters selected the same four rules.

- The empirical filter ran every rule against real grid data with no model involved, asking whether
  it fires when it should not and whether it discriminates. Across two independent extraction runs,
  `loading_pct > 100` was the only useful family, 10 of 10 both times.
- The textual filter read the source standards with no grid data, asking whether each rule is a
  faithful reading of the document. It kept `loading_pct > 100` and rejected the rest.

Each alone invites an objection — that the fire-rate cutoff is mistuned, or that the prompt is
wrong — and the `strict` arm shows the second objection can be correct. Both objections cannot
survive the convergence.

## 13. Limits

**The shield does not verify the contingency analysis.** Establishing whether losing line *k*
causes a violation requires a post-contingency power-flow solve, which is the computation the GNN
replaces. The supportable claim is that the shield catches unsafe-permissive predictions using
present-state standards, not that it verifies the model.

**The surviving rule is close to a tautology.**

| Grid | P(violation) | P(violation \| base already overloaded) |
|---|---:|---:|
| neurips2020 | 19.54% | 95.67% |
| case14 | 27.75% | 91.16% |
| wcci2022 | 24.76% | 94.74% |

Pure label restatement would give 100%. At 91–96% the rule carries real but partial information.
The shield enforces established N-1 doctrine and the data confirms that doctrine 91–96% of the
time. It is not discovering new physics.

**The doctrine is hand-written.** The gating logic in section 12 is code we wrote; the extraction
pipeline supplied the threshold. That doctrine belongs to the operational standards class that
section 14 shows is absent from the corpus.

**Three controls were never run.** A ceiling analysis (a decision tree on the 14 variables
targeting "the model was wrong", which upper-bounds what any rule system could catch), an
expert-written rule baseline as a never-merged third arm, and a rule-count ablation.

The ablation was answered structurally — only 16.2%, 0.51% and 30.9% of the model's errors sit
where a present-state rule could reach — and empirically, since a corpus can lose 29% of its rules
without changing anything. The expert baseline was not run, and it is what would separate
"extraction is the bottleneck" from "gating is the bottleneck".

## 14. Why the corpus is small

Per-document yield:

| Document | Candidates | Translated |
|---|---:|---:|
| NERC Reliability Standards (complete set) | 707 | 19 |
| GB Grid Code | 571 | 14 |
| Bangladesh Grid Code | 228 | 15 |
| TPL-001-5.1 (the N-1 standard) | 11 | 1 |
| NERC FAC-008-5 | 4 | 0 |

The two documents about post-contingency performance contributed 15 candidates between them.
TPL-001-5.1 produced only 5 distinct chunks, so the PDF on disk is a summary rather than the
standard carrying Table 1's P0–P7 contingency categories.

What TPL-001 did produce shows the problem:

```
Line | loading_pct > relay_loadability_limit_pct
Grid | power_oscillation_damping < acceptable_damping_threshold
```

Free variables, not numbers. This is structural rather than an extraction failure. NERC standards
are criteria-referencing by design: they say "within its applicable Facility Rating", and FAC-008
then requires each utility to hold its own documented methodology for computing that rating. The
number is deliberately never printed in the standard, so no prompt work can extract it.

The mismatch runs both ways.

The simulator is coarser than the standards regulate. Grid codes govern equipment — a generator's
power factor, a module's terminal voltage — while Grid2Op simulates a network of buses, lines and
aggregate flows. 1,332 candidates (54.1%) are blocked on two missing capabilities, frequency and
time. Grid2Op models no frequency at all, because quasi-static power flow assumes uniform system
frequency.

The standards are also silent about most of what the simulator provides. The surviving rules touch
4 of the 14 variables, and nothing in the corpus governs topology — no rule mentions line outages,
which is the subject of the task.

Grid codes govern connection and equipment compliance. Contingency screening is an operational
activity, written as process requirements such as "shall perform studies annually" rather than as
state predicates over telemetry. A layer built from connection codes cannot govern operations,
because the corpus was never about operations.

Do not write that what the simulator provides can be governed by the rules that survived. It is
false at 4/14 coverage.

Better documents would help only partly. PJM Manual 14B does print literal post-contingency numbers
(0.92–1.05 pu). But a complete document set supplies two predicates: post-contingency thermal,
which the corpus already yields, and post-contingency voltage, which is inert on these grids. Most
of the gain would be further restatements of the rule already in hand.
